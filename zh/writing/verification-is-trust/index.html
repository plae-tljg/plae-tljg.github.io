    03 验证才是信任：测试、权限与唤醒成本

    2026 年 10 月 1 日·8 分钟草稿预览

    AI 维护能不能被信任，不取决于模型判断得对不对，而取决于检查器的形状。本文从“规则和测试同源”的失败场景出发，讨论四类测试、可审核的边界、工具强制的权限，以及运行时兜底与维护轮的唤醒成本。

    0. 上篇留下的问题

    上篇处理了代码与数据的边界：什么应该声明成数据，什么时候才值得从通用实体提升为领域表。它留下了数据侧的结构。

    但结构存在不等于结构正确。AI 改了数据、加了规则、提升了一张表之后，下一个问题立刻出现：

    我们怎么知道这次改动真的让系统变好了？

    这篇处理验证、权限与唤醒成本。

    1. 一个全绿的失败

    一个 agent 接到任务：系统答不出某类问题。

    它看了几条未命中问题，写了一条新规则，又写了一条测试：

    CI 全绿。规则上线。

    但真实流量里，用户问的是：

    系统仍然拒答。

    问题不是 agent 不够聪明，而是：

    规则和测试来自同一批问句、同一个来源。测试只证明了这条规则能覆盖 agent 刚刚看过的那几句话。

    修复一个例子，和让系统真正知道一类问题，是两件不同的事。这件事的教训可以推广成一句更锋利的话：

    信任不来自 AI 判断得对不对，来自检查器的形状。

    后面的测试、权限和成本，都是围绕这句话展开的。

    2. 测试是验收标准，不是质量附录

    在 AI 维护里，测试不是“验证 AI 写的代码”，而是规定什么算“变好”。

    2.1 四类测试

    类型断言防什么
    正例应该回答，且落到正确数据规则过严、永远不命中
    易混负例长得像，但不应该命中规则过松、抢别人的问题
    拒答没依据时拒答编造
    歧义两个候选同样接近时拒答随便挑一个

    后三类最好在 AI 开始编辑之前由人种下。原因就是第 1 节的自证循环：

    如果测试和规则都由 AI 从同一批失败里生成，它们会一起变绿，而真实流量继续拒答。

    这也是为什么“测试通过”不能直接等于“维护完成”。测试只是检查器；检查器的形状决定它能发现什么、漏掉什么。

    2.2 断言要粗

    最好断言“答案包含某个事实”，而不是“等于某句完整文本”。

    一个改措辞就报警的测试集，人很快会学会忽略它；一旦被忽略，它就死了。这是关于人类注意力稀缺的论断：

    验证系统的成本不只是机器时间，还包括人认真看它的意愿。

    2.3 测试本身也是数据

    加一个问法是加模式；加一条保证是加测试。两者都应该是可比较差异的数据。

    2.4 数据 / git / CI 之间的账

    这里有一个常见问题：

    如果测试也是数据，为什么不把它们放进数据库里，而放在 git 文件里？

    因为测试不是运行时知识。运行时读取的是“如何回答”；测试回答的是“什么算对”。两者生命周期不同：

    • 知识要被执行；
    • 测试要 gate 一次改动。

    一个程序化的发布流程其实更长：

    核心不是 GitHub，而是：

    • main 上测试全绿；
    • 分支变红就是回归；
    • git revert 提供回滚。

    回归证据住在 git / CI 里，这一点和“把可声明的都搬到数据侧”看起来冲突。处理方式是分清楚：

    运行时知识必须声明进数据；验证证据可以是 gate 的一部分，但必须可追溯到具体改动。

    如果未来的系统需要一个非 git 的评审界面，那时才需要把提案 / 测试结果变成表。不是现在。

    2.5 死行与歧义报告

    除了四类测试，还需要：

    • 从未命中的知识行；
    • 会匹配多个候选的问法；
    • 新规则是否覆盖旧规则的范围；
    • 真实未命中问题按形状聚类。

    这些检查决定“该加规则”还是“该改结构”。

    3. 权限：谁有权改什么

    验证要成立，边界必须是真的。

    3.1 “请不要越界”不是边界

    把边界写进提示词是请求，不是约束。只要 agent 有 shell、文件系统和数据库，它就可能直接写库、改引擎、改测试来让测试通过。

    可维护的系统需要工具强制：

    3.2 为什么

    原则：

    回答用户和写系统状态，不应该由同一个进程同时拥有权限。

    如果 AI 在请求路径上既能回答又能写知识，错误答案会立刻变成“系统知识”，没有评审，没有回滚。

    即使不在运行时，agent 直接改在线数据库也有问题：改动不在差异里，评审看不到，重建后可能被覆盖。

    3.3 两种合法写入

    PR / 差异：改离线文件，开分支，跑测试，开 PR，人合并。评审、历史、回滚都由 git 提供。

    提案表：当评审者不使用 git，或者需要在不合并的情况下快速学习时，才需要 proposals + 审核界面 + 状态机 + 发布路径。这是例外，不是默认。

    3.4 允许面要足够

    边界太严也会失败：如果 agent 不能读数据、看统计、跑测试，它为了完成任务会去找绕路。

    一个可用的边界通常包括：

    • 只读数据查询；
    • 内容文件读写；
    • build / test 命令；
    • 未命中问题和统计查看；
    • 明确的提交方式。

    3.5 角色权限表

    角色读写不能
    终端用户自己的对话提问 / 操作看内部数据
    运营面板、评审队列发布决策改引擎
    AI 维护者只读投影、证据、内容内容 / 提案直接写在线表、合并
    开发者全部引擎 /表结构/ 迁移绕过评审
    运行时数据投影运行时状态改知识

    4. 唤醒成本

    4.1 三个账本

    来源次数与什么成正比处理
    A. 运行时兜底请求数 ×（1 − 覆盖率）尽量不用；用了也保留证据
    B. 维护轮结构变化频率批量、离线、经测试和评审
    C. 构建 / 同步数据量0 次模型调用

    目标：

    让 AI 调用与结构变化成正比，而不是与流量或数据变化成正比。

    4.4 唤醒策略

    模式适合场景风险
    每请求冷启动、首次探索成本不可控
    微批量高峰后补学习反馈延迟
    每日 / 每周稳定业务、批量评审新问题多时慢
    事件触发新目录、新政策阈值难调
    手动低流量、高敏感长期不更新

    4.5 兜底不等于系统知道

    模型兜底可以是一个可选层，但必须：

    • 由人决定开启；
    • 回答过的问题仍记录为未解决；
    • 模型只看到相关实体，而不是全库；
    • 超时 / 报错 / key 失效时安全地拒答。

    原因：

    回答访客，不等于系统知道。

    5. 两个真实案例作为证据

    5.1 personal-chatbots

    一个最小实现：5 张表、离线内容、运行时投影、messages 在线表。截至写作时：

    • 24 条知识行；
    • 48 条 frozen cases；
    • 单元与不变量测试；
    • 浏览器版跑同一组 frozen cases，CI 做 parity 检查。

    它证明的是：上述结构可以小到什么程度。 它还证明了另一件更窄的事：确定性层约 0.2 ms、0 token；模型兜底约 7 秒。差的不是 token 单价，是唤醒位置。

    5.2 MaaFwPhoneAI

    第二个域是 Android GUI 自动化：

    • workflow 是数据库里的 MaaFramework 流水线图；
    • AI 只写提案，评审后成为在线流水线；
    • 每次执行保存后置条件与证据；
    • 已验证流程进入 0 token 回放。

    PC 原型已经验证了“AI 跑通一次，之后 0 token 回放”；Android 端仍在收敛。它证明结构逻辑不依赖文本域，也暴露了更多运行时复杂度。

    6. 说明与边界

    • 四类测试只认证已知的失败类别；它不能证明未知情况下也对。
    • 测试和规则同源的问题，本文没有完全解决。要解决它，需要让验证器的一部分独立于被验证者，这可能是下一阶段的工作。
    • 如果模型变得足够便宜、稳定、可审计，运行时 agent 的缺陷会减小；但这套结构仍然解决“可累积、可回滚”。
    • 如果一次改动的评审成本长期高于直接改代码，这套结构不划算。
    • 作者立场：我不认为“让 AI 自己判断自己”能成为长期信任机制；信任必须来自独立的检查器。
    • 这套方法最大的代价是评审带宽。自动化可以提高检查速度，但不能自动产生判断。
