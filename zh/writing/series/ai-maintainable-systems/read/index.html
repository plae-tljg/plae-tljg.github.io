01 快速原型之后：代码、数据与结构

1. 一个很典型的周五下午

假设你想快速做一个聊天机器人，或者任何会用上 AI 的小应用。你想验证的是“有没有人用”，不是“能不能写成教科书架构”。于是你很自然地不想写数据访问层、迁移、权限、渠道、读写模块和评审流程。

然后你看到两条捷径。

捷径一：把 agent 当后端。

# 伪代码：把 agent 命令包成一个 API
import subprocess
from fastapi import FastAPI

app = FastAPI()

@app.post("/chat")
def chat(question: str):
    result = subprocess.run(
        ["claude", "-p", question],   # 或 opencode -c、其他 agent 命令
        capture_output=True, text=True,
    )
    return {"answer": result.stdout}

用户请求进来，直接转给 agent。你不写表结构、权限、渠道、读写模块，一个下午就能演示。这不是在写系统，是在让 agent 临时扮演整个系统。

捷径二：先写硬编码，再让 agent 维护。

if "price" in question and "iphone" in question:
    return "iPhone is $999."

if "refund" in question:
    return "Refunds are available within 14 days."

它运行时更稳定、更便宜。快速原型阶段，这是合理选择。问题是之后：价格变了改分支，问法变了加分支，错误丢给 agent 改代码；重复几十次后，没有人能完整说出系统现在知道什么。

2. 低流量下，两条捷径都可能是对的

必须承认一个反例：

如果原型只活三天，流量很低，模型便宜到可以忽略，系统几乎不变化——两条捷径都是理智的。

短路原型不是罪，把一次性原型当成会持续成长的系统才是。

所以真正要判断的是：

  • 它会不会持续变化？
  • 变化时需不需要被验证？
  • 除了作者，还有没有人需要评审 / 理解它？
  • 出错时，损失只是一次 demo，还是客户已经依赖它？

只要有一个答案是“是”，捷径就会开始变贵。但它们共同的问题不是“用了 agent”或“用了硬编码”，而是：

系统没有给变化一个可验证的落点。

Agent 当后端，落点不存在；硬编码 + agent 维护，落点是最难验证的代码。

3. 一个太快得出的结论

到这里，很容易得出结论：

那就让 AI 改数据，不要改代码。数据比代码更适合 AI 维护。

这个结论走得太快了，而且会把整季带向一个错误前提。

它错在两点：

  1. 代码不是坏的。 算法、副作用、性能、安全边界、事务、外部系统交互，本来就应该由代码表达。
  2. 数据不是自动可维护的。 一堆没有词汇、没有表结构、没有校验的 JSON，只会把结构藏进约定里，比代码更难验证。

真正的问题不是“代码还是数据”，而是：

哪些东西应该被声明成数据，哪些必须留在代码，边界在哪里，谁负责守边界。

“数据比代码高级”是一种偷懒的说法；正确的问题是结构放在哪里。

4. 代码和数据是两种材料

可以把代码和数据当成两种材料，而不是两个等级。

代码数据
擅长算法、副作用、I/O、性能、安全、不变量事实、规则、文案、配置、内容
可验证性依赖测试、运行路径、边界可寻址、可比较差异、可校验
爆炸半径调用链、时序、异常路径通常限制在行 / 实体 / 规则
修改者开发者 + AI（高风险）人和 AI（可评审）
失败方式运行到某条路径才发现写入时可以被拒绝

数据更适合 AI 维护，不是因为数据更高贵，而是因为：

  • 它可以有稳定标识；
  • 改动通常是局部的；
  • 上下文可以裁剪；
  • 可以被幂等重建；
  • 可以在写入时校验。

但这些性质只对有结构的数据成立。自由文本和乱放 JSON 不具备它们。

代码仍然承担它擅长的工作：定义 原语、执行算法、处理副作用、守住安全边界。代码不是被“搬掉”，而是退到更少、更稳定的位置：

System = Code + Data

代码负责解释、校验、执行、审查；数据负责承载知识、规则、变量、流程和状态。

当代码只解释词汇表、不逐条实现业务时，它接近 meta-code（元代码）：

如果代码规模随领域对象数量增长，它是业务代码； 如果代码规模只随词汇表大小增长，它才配叫 meta-code。

5. 什么时候应该把行为放进数据

不是所有东西都应该数据化。一个判断清单比口号有用：

  • 变化频率：它经常变吗？经常变的事实更适合数据。
  • 可寻址性：能给它一个稳定标识吗？价格、规则、文案可以；一段控制流通常不行。
  • 评审需求：改动需不需要被非程序员看懂？
  • 验证方式：能不能写测试 / 校验，而不是只能靠运行？
  • 爆炸半径：改错了影响一行，还是一条调用链？
  • 上下文大小：AI 能不能只读一小块就完成修改？

反过来，以下通常应该留在代码：

  • 算法和性能敏感路径；
  • 外部副作用和 I/O；
  • 并发、事务、安全边界；
  • 无法用数据词汇表达的原语。

这不是“把代码搬空”，而是把可声明的知识从代码里拿出来，让代码只保留它最擅长的部分。

5.1 一个最小规则：值不进句子

变化速度比句子更快的东西，不要写进句子里。

价格、版本、库存、日期、star 数属于数据；句子属于模板。这样一次数据变化只需要改一行、做一次重建，而不是改 N 条答案，更不需要唤醒模型。

6. 结构是边界，不是口号

当你说“用结构”，具体指的是什么？至少包含五件事：

  1. 数据用什么词汇表达（实体类型、关系类型、动作类型）；
  2. 数据用什么形态承载（行、JSON、文件、列）；
  3. 哪些字段被声明、哪些留着自由；
  4. 谁来校验、谁来评审、怎么回滚；
  5. 状态和构建产物怎么分开。

结构不是“表越多越好”，也不是“代码越少越好”。它是一份关于边界的契约。

这个契约里最困难的一条是：

通用化到哪一步，领域特定化到哪一步？

7. 核心张力：通用数据 vs 领域表

一个具体例子会让这个张力变清楚。

商品可以写成通用实体：

{
  "entity_type": "product",
  "key": "sku:iphone-17",
  "attrs_json": { "price_cents": 99900, "stock": 12 }
}

好处是扩展便宜：新增领域不用迁移，AI 加数据就行。

但三个月后，你可能会看到：

{"price_cents": 99900}
{"price": 999}
{"priceCents": 99900}
{"price_usd": "999.00"}

命名开始漂移；价格可以是负数；库存可以是字符串；“上架但无价格”没人知道是否合法。查询也变丑：每次都要写 json_extract，性能依赖约定。

另一个极端是建 products 表：类型、约束、查询都强，但每次领域变化都要迁移，AI 不能再靠“加数据”扩展。

于是问题不是“数据化还是代码化”，而是：

  • 通用数据用扩展性换结构强度；
  • 领域表用结构强度换演化成本；
  • 选择取决于当前哪种成本更痛。

这就是数据与代码的辩证：不是谁更高级，而是结构放在哪一层。

8. 失败条件与作者立场

这套方法什么时候不成立？

  • 如果系统几乎不变化，结构投入收不回来；
  • 如果模型便宜、稳定、可审计到可以接受运行时 agent，临界点会移动；
  • 如果每次变化都需要新增 原语，而不是新增数据，通用结构就失败了；
  • 如果维护成本长期高于直接改代码，结构就是不划算的。

作者立场：我不认为“数据比代码好”或“代码比数据好”是有意义的争论。有意义的问题是：

这部分行为的变化频率、验证需求和爆炸半径，决定了它应该住在代码还是数据；而边界必须被明确声明，而不是靠约定维持。

9. 下一个问题

现在框架有了：代码和数据是两种材料，结构是两者的边界契约，核心张力是通用数据 vs 领域表。

但边界具体怎么划？什么时候一个“可以有通用实体”的项目，真的需要一张 products 表？为什么不是永远不需要？

下一篇专门处理这个问题：数据化的边界。

02 什么时候才需要一张 products 表？——数据化的边界

0. 上篇留下的边界问题

上篇的结论是：代码和数据是两种材料，结构是两者的边界契约；其中最困难的一条是 通用数据 vs 领域表。它停在了一个具体问题上：

entities + entity_links + attrs_json

商品可以只是：

{
  "entity_type": "product",
  "key": "sku:iphone-17",
  "attrs_json": { "price_cents": 99900 }
}

但这立刻带来一个问题：

既然商品可以是通用实体，为什么还需要 products 这种领域表？
如果永远不需要，结构住在哪里？
如果需要，为什么不是一开始就需要？

这篇不急着给答案。先把两个极端都推到失败，再从失败里推导边界。

1. 先认真待在“全通用”这一端

假设我们真的坚持：

  • 没有 products 表；
  • 没有 有类型的列；
  • 所有业务事实都放进 attrs_json。

一开始它很好用：新增领域不用迁移，AI 加几行数据就行。

然后系统开始变大。第一个失败是命名漂移。

三个月后，查询价格时你可能看到：

{"price_cents": 99900}
{"price": 999}
{"priceCents": 99900}
{"price_usd": "999.00"}

没有人故意制造分歧；只是不同的人、不同的 agent、不同的时间，做了不同的命名选择。数据库没有拒绝过任何一条。

第二个失败是校验退化：

  • 价格可以是负数；
  • 单位可以是 USD、HKD，也可以没有；
  • “库存”可以是数字、字符串或缺失；
  • 已下架商品可能仍然有价格，但没人知道这是不是合法状态。

第三个失败是查询变丑：

SELECT *
FROM entities
WHERE entity_type = 'product'
  AND json_extract(attrs_json, '$.price_cents') > 10000
  AND status = 'live'

一旦这种查询变多，性能、索引和可读性都会开始付代价。

这说明：

通用化不会消灭结构，它只是把结构从表结构转移到了约定、命名和查询里。

结构变成了重建结构：每个读它的人、每个 AI 会话、每次调试，都要重新把它拼出来。

1.1 声明结构与重建结构

同样的结构，可以住在两个地方：

  • 声明结构：列、约束、词汇表。写的时候声明一次，引擎和数据库会读它；
  • 重建结构：命名约定、注释、JSON key。每个读者、每个 AI 会话、每次查询，都要重新把它拼出来。

目标不是消灭结构，而是最小化重建结构。

1.2 交接说明有多长

一个可操作的检验：

交接说明有多长？ AI 或新维护者行动前需要被告知的每句话，都是还没有声明出来的结构。

但声明结构也有成本：迁移、耦合、一个设计错的列删起来比加更难。所以目标不是结构越少越好，而是把必须保留的声明结构压到足够小。

2. 再认真待在“每个领域一张表”这一端

另一个极端是每来一个领域就建表：

products
orders
coupons
flows
rules
...

它查询方便、约束强、团队熟悉。但代价是：

  • 新领域需要迁移和部署；
  • AI 不能真正扩展系统，只能改已有领域；
  • 很多结构重复：状态、来源、时间、审计；
  • 领域一变化，表结构跟着变。

它的失败方式不是“无法表达”，而是“无法轻量演化”。

3. 不急着合成：用同一种货币比较

两个极端不是“一个更先进”，而是把同一种成本放到了不同地方。可以用四个维度比较：

维度全通用实体每领域一张表
新增领域加数据，0 迁移加表，1 迁移
查询和约束弱，依赖 JSON 和约定强，数据库可强制
可读性与交接说明每个读者要自己重建表结构直接说明
演化成本低（数据层），高（语义层）低（语义层），高（表结构层）

真正的问题不是“要不要领域表”，而是：

把结构放在约定里，还是放在表结构里？
哪一种成本在当前系统里更痛？

4. 从失败推导提升条件

提升条件不应该是清单，而应该是从上面失败里推出来的。

4.1 当数据不再是“东西”

订单行、库存流水、价格历史不是实体，它们是事件 / 状态变化。把事件硬塞进 attrs_json 会让查询和时间关系变得别扭。这时需要事实表。

4.2 当数据库能强制、而校验器很难强制

多列唯一、外键、跨行 CHECK 这类约束，数据库天然更强。如果这些约束是业务正确性的前提，就值得提升。

4.3 当查询痛苦是测量出来的，不是想象出来的

JSON 查询慢不是因为你“感觉 50k SKU 会慢”，而是因为：

  • 有真实慢查询；
  • 有真实索引需求；
  • 有真实聚合和排序。

measure 之后再拆。

4.4 当外部表结构不允许你选择

对接 ERP、支付、库存系统时，对方给你一个固定表结构。你不再设计它，只能适配。

4.5 两个反例

上面这些条件成立，也可能还不该提升：

  • 数据量很大，但查询很少、很冷，瓶颈不在 JSON；此时优化可能只是早期复杂化。
  • 查询很痛，但可以通过物化视图或索引优化解决，不一定要改主模型。

上面这些条件不成立，也可能必须提升：

  • 外部表结构强迫你；即使内部没有查询痛点，也得上表。

所以提升不是规则表，而是：

当某一种成本真实地压过了另一种，才移动边界。

5. 一次真实的提升：知识模板不动

下面演示一次提升，重点不是 SQL 多优雅，而是知识层不用改。

5.1 提升前

实体行：

{
  "entity_type": "product",
  "key": "sku:iphone-17",
  "attrs_json": { "price_cents": 99900 }
}

知识行：

- slug: product.price
  patterns: ["how much is {product}"]
  slots: { product: product }
  action:
    kind: answer
    template: "{product} is {price}."

测试：

- name: product.price.iphone
  question: "how much is iphone-17"
  expect:
    resolves: { product: "sku:iphone-17" }
    answer_contains: ["999.00"]

5.2 提升后

新增 products 表，实体主干仍然保留：

CREATE TABLE products (
  entity_id    INTEGER PRIMARY KEY REFERENCES entities(id),
  price_cents  INTEGER NOT NULL,
  currency     TEXT NOT NULL DEFAULT 'USD',
  stock        INTEGER NOT NULL DEFAULT 0
);

存储层读价格时，从 products 取，而不是从 attrs_json 取。但：

  • 知识模板（knowledge）仍然是 {product} 和 {price}；
  • 解析器返回的上下文仍然包含 price；
  • 测试用例不需要重写；
  • 变的只是数据投影和 SQL。

这就是参数化的回报：

存储形态可以变，知识的句子不用变。

6. 领域表也是一次命名行为

还有一层经常被忽略：products 这个词本身在替未来读者做命名工作。

entity_type='product' + 词汇表条目，把“这是什么东西”的定义分散在代码、数据、文档和人的记忆里；products 表把这份定义声明在一个地方。

这是它的优势，也是它的成本：

  • 优势：交接说明变短，读者更快知道这里放什么；
  • 成本：命名一旦公开就很难改，表的耦合会把未来的选择锁住。

所以“领域表 = 命名行为”不是一句修辞，它意味着提升时要额外问：

这个名字是否稳定到值得成为表结构的一部分？

如果答案不确定，也许先让它以 词汇表 / entity_type 的形式存在，等证据足够再固化。

7. 四个家：结构最终住在哪里

无论提升与否，结构都要分到四个家：

家谁改改动意味着
配置人一次部署
内容人和 AI（经评审）一次 PR
数据构建流程一次重建
状态运行时追加；永不重建

进一步两条线：

  • 离线 / 在线：内容离线可比较差异；投影在线可查询；运行时只读投影；
  • 构建 / 在线：构建表无状态；状态只在在线表。

这四条边界比“有没有 products 表”更重要。它们决定了：

  • AI 改的是哪一层；
  • 重建 会不会伤害状态；
  • 评审看到的是什么；
  • 一个新增结构应该落到哪里。

7.1 状态也要被赚得

领域表不是唯一会被过度建立的东西，状态表也一样。

“第二个”可以从上一轮引文重写出来，不需要状态表；只有某个值必须跨轮保留（“几个人？” -> “3”）时，流程与状态才值得存在。反过来，GUI 自动化里的步骤状态是真需求，因为识别与动作本来就有先后和分支。MaaFwPhoneAI 就是一个状态必须被建出来的域。

所以状态不是禁忌，而是必须由跨轮值或副作用来赚得。

8. 说明与边界

  • 本文不主张“永远不要领域表”。它主张的是：提升由真实成本触发，而不是由直觉触发。
  • 如果业务天然要求强事务、强约束、大量查询，领域表可能第一天就该存在。
  • 如果团队没有能力维护表结构，通用实体更合适；如果团队没有能力维护约定，领域表更合适。
  • 作者倾向于：先用通用结构换演化速度，等一种成本真实地压过另一种，再提升。

9. 下一个问题

数据化的边界有了，知识句子的稳定性也有了。但还有一个问题没有回答：

AI 改了数据 / 结构之后，我们怎么知道这次改动真的让系统变好了？

这正是下一篇的主题：验证、权限与唤醒成本。

03 验证才是信任：测试、权限与唤醒成本

0. 上篇留下的问题

上篇处理了代码与数据的边界：什么应该声明成数据，什么时候才值得从通用实体提升为领域表。它留下了数据侧的结构。

但结构存在不等于结构正确。AI 改了数据、加了规则、提升了一张表之后，下一个问题立刻出现：

我们怎么知道这次改动真的让系统变好了？

这篇处理验证、权限与唤醒成本。

1. 一个全绿的失败

一个 agent 接到任务：系统答不出某类问题。

它看了几条未命中问题，写了一条新规则，又写了一条测试：

- name: rule.new_case
  question: "can I get a refund?"
  expect:
    answers: true

CI 全绿。规则上线。

但真实流量里，用户问的是：

“What is your refund policy?”
“Can I cancel and get my money back?”
“How long do refunds take?”

系统仍然拒答。

问题不是 agent 不够聪明，而是：

规则和测试来自同一批问句、同一个来源。测试只证明了这条规则能覆盖 agent 刚刚看过的那几句话。

修复一个例子，和让系统真正知道一类问题，是两件不同的事。这件事的教训可以推广成一句更锋利的话：

信任不来自 AI 判断得对不对，来自检查器的形状。

后面的测试、权限和成本，都是围绕这句话展开的。

2. 测试是验收标准，不是质量附录

在 AI 维护里，测试不是“验证 AI 写的代码”，而是规定什么算“变好”。

2.1 四类测试

类型断言防什么
正例应该回答，且落到正确数据规则过严、永远不命中
易混负例长得像，但不应该命中规则过松、抢别人的问题
拒答没依据时拒答编造
歧义两个候选同样接近时拒答随便挑一个

后三类最好在 AI 开始编辑之前由人种下。原因就是第 1 节的自证循环：

如果测试和规则都由 AI 从同一批失败里生成，它们会一起变绿，而真实流量继续拒答。

这也是为什么“测试通过”不能直接等于“维护完成”。测试只是检查器；检查器的形状决定它能发现什么、漏掉什么。

2.2 断言要粗

最好断言“答案包含某个事实”，而不是“等于某句完整文本”。

一个改措辞就报警的测试集，人很快会学会忽略它；一旦被忽略，它就死了。这是关于人类注意力稀缺的论断：

验证系统的成本不只是机器时间，还包括人认真看它的意愿。

2.3 测试本身也是数据

- name: confusable.price-not-a-product-question
  question: "what is the price of dsh-review?"
  expect:
    refuses: true

加一个问法是加模式；加一条保证是加测试。两者都应该是可比较差异的数据。

2.4 数据 / git / CI 之间的账

这里有一个常见问题：

如果测试也是数据，为什么不把它们放进数据库里，而放在 git 文件里？

因为测试不是运行时知识。运行时读取的是“如何回答”；测试回答的是“什么算对”。两者生命周期不同：

  • 知识要被执行；
  • 测试要 gate 一次改动。

一个程序化的发布流程其实更长：

agent 编辑内容 -> 跑测试 -> 开 PR -> CI -> 人合并

核心不是 GitHub，而是：

  • main 上测试全绿；
  • 分支变红就是回归；
  • git revert 提供回滚。

回归证据住在 git / CI 里，这一点和“把可声明的都搬到数据侧”看起来冲突。处理方式是分清楚：

运行时知识必须声明进数据；验证证据可以是 gate 的一部分，但必须可追溯到具体改动。

如果未来的系统需要一个非 git 的评审界面，那时才需要把提案 / 测试结果变成表。不是现在。

2.5 死行与歧义报告

除了四类测试，还需要：

  • 从未命中的知识行；
  • 会匹配多个候选的问法；
  • 新规则是否覆盖旧规则的范围；
  • 真实未命中问题按形状聚类。

这些检查决定“该加规则”还是“该改结构”。

3. 权限：谁有权改什么

验证要成立，边界必须是真的。

3.1 “请不要越界”不是边界

把边界写进提示词是请求，不是约束。只要 agent 有 shell、文件系统和数据库，它就可能直接写库、改引擎、改测试来让测试通过。

可维护的系统需要工具强制：

read:  content/**, read-only projection
write: content/** (or proposals)
deny:  engine/**, schema, direct live writes, merge

3.2 为什么

原则：

回答用户和写系统状态，不应该由同一个进程同时拥有权限。

如果 AI 在请求路径上既能回答又能写知识，错误答案会立刻变成“系统知识”，没有评审，没有回滚。

即使不在运行时，agent 直接改在线数据库也有问题：改动不在差异里，评审看不到，重建后可能被覆盖。

3.3 两种合法写入

PR / 差异：改离线文件，开分支，跑测试，开 PR，人合并。评审、历史、回滚都由 git 提供。

提案表：当评审者不使用 git，或者需要在不合并的情况下快速学习时，才需要 proposals + 审核界面 + 状态机 + 发布路径。这是例外，不是默认。

3.4 允许面要足够

边界太严也会失败：如果 agent 不能读数据、看统计、跑测试，它为了完成任务会去找绕路。

一个可用的边界通常包括：

  • 只读数据查询；
  • 内容文件读写；
  • build / test 命令；
  • 未命中问题和统计查看；
  • 明确的提交方式。

3.5 角色权限表

角色读写不能
终端用户自己的对话提问 / 操作看内部数据
运营面板、评审队列发布决策改引擎
AI 维护者只读投影、证据、内容内容 / 提案直接写在线表、合并
开发者全部引擎 /表结构/ 迁移绕过评审
运行时数据投影运行时状态改知识

4. 唤醒成本

4.1 三个账本

来源次数与什么成正比处理
A. 运行时兜底请求数 ×（1 − 覆盖率）尽量不用；用了也保留证据
B. 维护轮结构变化频率批量、离线、经测试和评审
C. 构建 / 同步数据量0 次模型调用

目标：

让 AI 调用与结构变化成正比，而不是与流量或数据变化成正比。

4.2 成本公式和一个警告

N  = 每周期请求数
c0 = 确定性解析单次成本
ca = 运行时兜底单次成本
κ  = 确定性覆盖率
w  = 每周期维护唤醒次数
cm = 单次维护成本（模型 + 上下文 + 人工评审）

C(N, w) = N * [c0 + (1 - κ) * ca] + w * cm

如果一次维护把覆盖率提高 Δκ：

benefit = N * Δκ * ca
值得做当且仅当 N * Δκ * ca > cm

但这个公式有几个强假设，值得写清楚：

  • 维护成本对 w 近似线性——上下文和评审摊薄后可能成立，也可能不成立；
  • Δκ 不递减——实际上越往后提升越难；
  • 增加结构不会抬高 c0——规则越多，解析可能越慢。

所以公式不是预言，是一个用来问“这轮维护值不值”的框架。

4.3 一个示意算例

N = 10,000 请求/天，ca = 0.01，cm = 0.50
覆盖率从 90% 到 92%：benefit = 2 > 0.50
覆盖率只提高 0.1%：benefit = 0.1 < 0.50

数字仅用于说明。

4.4 唤醒策略

模式适合场景风险
每请求冷启动、首次探索成本不可控
微批量高峰后补学习反馈延迟
每日 / 每周稳定业务、批量评审新问题多时慢
事件触发新目录、新政策阈值难调
手动低流量、高敏感长期不更新

4.5 兜底不等于系统知道

模型兜底可以是一个可选层，但必须：

  • 由人决定开启；
  • 回答过的问题仍记录为未解决；
  • 模型只看到相关实体，而不是全库；
  • 超时 / 报错 / key 失效时安全地拒答。

原因：

回答访客，不等于系统知道。

5. 两个真实案例作为证据

5.1 personal-chatbots

一个最小实现：5 张表、离线内容、运行时投影、messages 在线表。截至写作时：

  • 24 条知识行；
  • 48 条 frozen cases；
  • 单元与不变量测试；
  • 浏览器版跑同一组 frozen cases，CI 做 parity 检查。

它证明的是：上述结构可以小到什么程度。 它还证明了另一件更窄的事：确定性层约 0.2 ms、0 token；模型兜底约 7 秒。差的不是 token 单价，是唤醒位置。

5.2 MaaFwPhoneAI

第二个域是 Android GUI 自动化：

  • workflow 是数据库里的 MaaFramework 流水线图；
  • AI 只写提案，评审后成为在线流水线；
  • 每次执行保存后置条件与证据；
  • 已验证流程进入 0 token 回放。

PC 原型已经验证了“AI 跑通一次，之后 0 token 回放”；Android 端仍在收敛。它证明结构逻辑不依赖文本域，也暴露了更多运行时复杂度。

6. 说明与边界

  • 四类测试只认证已知的失败类别；它不能证明未知情况下也对。
  • 测试和规则同源的问题，本文没有完全解决。要解决它，需要让验证器的一部分独立于被验证者，这可能是下一阶段的工作。
  • 如果模型变得足够便宜、稳定、可审计，运行时 agent 的缺陷会减小；但这套结构仍然解决“可累积、可回滚”。
  • 如果一次改动的评审成本长期高于直接改代码，这套结构不划算。
  • 作者立场：我不认为“让 AI 自己判断自己”能成为长期信任机制；信任必须来自独立的检查器。
  • 这套方法最大的代价是评审带宽。自动化可以提高检查速度，但不能自动产生判断。

04 附录：推导模板、清单与术语表

这不是正文，而是前 3 篇的配套工作文档。

1. 推导链

不要从“用哪张表 / 哪个 agent”开始，而从目标和约束开始：

Goal -> Actors -> Intents -> Information shapes
     -> Structures -> Columns -> IO -> Wake policy

1.1 Goal

一句话：为谁解决什么。包含终端用户、他们要完成什么、哪些事情必须由人接手。

1.2 Actors

至少区分：

角色关心什么
终端用户是否被回答 / 操作是否完成
运营 / 客户知识是否正确、能否评审发布
AI 维护者读什么、写什么、如何验证
开发者引擎、表结构、迁移、权限

1.3 Intents

列真实意图：查事实、查实体属性、条件判断、多轮澄清、副作用 / 交人、未知。

1.4 Information shapes

形态适合结构
静态事实知识行 / 文案
参数化事实模板 + 实体行
条件路由规则行 / 小 DSL
跨轮指代projection，不用状态表
多轮收集流程 + 状态
副作用task / 外部动作
未知拒答 + 收件箱
复合问句解析算法，不是表

1.5 Structures

  • 放配置、内容、数据还是状态？
  • 优先：配置文件 > 内容文件 > 已有表 > 新表；
  • 默认：通用实体 + link + JSON 属性 + 小词汇表；
  • 提升由真实成本触发，不由直觉触发。

1.6 Columns

  • 会查询、连接、过滤、约束、统计的字段 -> 有类型的列；
  • 领域相关、只随行携带的字段 -> JSON；
  • 需要双向关系 -> link 表；
  • 不再是实体形状 -> 独立事实表。

1.7 IO

角色读写
终端用户对话提问 / 操作
运营面板、评审队列发布决策
AI 维护者只读证据、内容内容 / 提案
运行时数据投影运行时状态

1.8 唤醒策略

  • 运行时是否允许模型兜底？
  • 维护是每日、事件触发还是手动？
  • 哪些数据变化根本不需要模型？
  • 模型回答过的未命中是否保留证据？

2. 一个练习：预约助手

目标：用户可以预约，复杂预约交给人工。

IntentShapeStructure
营业时间静态事实知识行
有哪些服务参数化事实实体 + 模板
周末能不能约条件规则规则行
“第二个服务”指代上一轮引文
预约需要哪些信息多轮收集流程 + 状态
提交后通知工作人员副作用task
未知政策未知拒答 + 收件箱

3. 结课清单

问题

  • 我面对的是运行时 agent 不稳定，还是硬编码维护不可验证？
  • 问题会持续成长，还是一次性？
  • 我是否把“修好一个例子”当成“变好”？

结构

  • 业务事实还有多少住在代码里？
  • 配置、内容、数据、状态是否分开？
  • 离线 / 在线、构建 / 运行时边界是否清楚？
  • 值进句子了吗？
  • 新结构有真实触发条件吗？

验证

  • 每个行为改动有测试吗？
  • 有正例、易混负例、拒答、歧义四类吗？
  • 有回归基线和回滚路径吗？
  • 有死行 / 歧义报告吗？

权限

  • AI 的读 / 写 / 禁止集合是什么？
  • 权限是工具强制还是 prompt 请求？
  • AI 能否直接写在线表、直接合并？
  • 评审能否在有限上下文内完成？

成本

  • 运行时唤醒几次？维护唤醒几次？
  • 哪些变化会唤醒模型？
  • 兜底是否仍记录 unresolved？
  • 覆盖率、兜底率、单位成本有记录吗？

4. 反模式

  • 把所有逻辑塞进代码；
  • 把 agent 放在运行时；
  • 让 agent 直接改在线状态；
  • 没有测试就让 agent 维护；
  • 所有东西都塞 JSON；
  • 为未来预留空表；
  • 用模型兜底却清掉 unresolved；
  • 用模型回答来假装结构已经知道答案。

5. 什么时候不该用这套东西

一次性脚本、没有持续演化需求的小工具、完全没有重复决策的探索任务——简单脚本就是正确答案。

结构化有成本，不值得的时候不要用它。

6. 术语表

术语含义
可维护改动可执行、可验证、可回滚、可累积、可负担
结构代码与数据之间的契约：行、表结构、词汇、校验、流程
Data可声明层：知识、规则、变量、流程、测试、内容文件
meta-code代码规模随词汇表增长、而不是随领域增长的解释器 / 校验器 / 运行器
四个家配置 / 内容 / 数据 / 状态
离线 / 在线可编辑、可比较差异的形态 vs 可索引、可查询的投影
构建 / 在线构建表 vs 运行时状态表
重建结构未声明、每次都要重新推导的结构
指代从上一轮引文推导的跨轮引用，不需要状态表
流程 / 状态只有值必须跨轮保留时才需要的运行时状态
唤醒唤醒模型：运行时兜底 / 维护轮 / 构建
兜底（fallback）结构答不出时的模型回答；仍记录 unresolved
提案可审核、可回滚的改动；git PR 或提案表
κ确定性覆盖率
死行从未命中的知识行

7. 最后四个问题

如果 AI 改了一个数据 / 内容，你能回答下面四个问题，这个系统就在正确方向上：

  1. 为什么改？证据是什么？
  2. 改了什么？差异在哪里？
  3. 是否变好？测试和指标是否支持？
  4. 错了怎么退回去？

能回答，结构就是可维护的；不能回答，模型再强也只是更快地在黑箱里改东西。
