## 0. The Problem the Previous Essay Left

The previous essay handled the boundary between code and data: what should be declared as data, and when it is worth promoting a generic entity into a domain table. It left behind the structure on the data side.

But a structure existing does not mean the structure is right. Once AI has changed the data, added a rule, and promoted a table, the next question appears immediately:

> **How do we know this change actually made the system better?**

This essay covers verification, authority, and wake cost.

## 1. An All-Green Failure

An agent gets a task: the system cannot answer a certain kind of question.

It looks at a few missed questions, writes a new rule, then writes a test:

```yaml
- name: rule.new_case
  question: "can I get a refund?"
  expect:
    answers: true
```

CI is all green. The rule ships.

But in real traffic, users ask:

```text
“What is your refund policy?”
“Can I cancel and get my money back?”
“How long do refunds take?”
```

The system still refuses to answer.

The problem is not that the agent is not smart enough; it is that:

> **The rule and the test come from the same batch of questions, from the same source. The test only proves that this rule can cover the few sentences the agent just looked at.**

Fixing one example and making the system actually know a kind of question are two different things. The lesson generalizes into a sharper sentence:

> **Trust does not come from whether the AI judged correctly; it comes from the shape of the checker.**

The tests, authority, and cost that follow all unfold around this sentence.

## 2. Tests Are Acceptance Criteria, Not a Quality Appendix

In AI maintenance, tests are not about "verifying the code the AI wrote"; they define what counts as "better".

### 2.1 Four Kinds of Test

| Kind | Assertion | Guards against |
|---|---|---|
| Positive | Should answer, and land on the right data | Overly strict rules that never match |
| Confusable negative | Looks similar, but should not match | Overly loose rules that steal other people's questions |
| Refusal | Refuses when there is no basis | Fabrication |
| Ambiguity | Refuses when two candidates are equally close | Picking one arbitrarily |

The last three kinds are best planted by a human before the AI starts editing. The reason is the self-confirmation loop of Section 1:

> If both the tests and the rules are generated by the AI from the same batch of failures, they will turn green together while real traffic keeps being refused.

This is also why "tests pass" cannot simply mean "maintenance is done". A test is only a checker; the checker's shape decides what it finds and what it misses.

### 2.2 Assertions Should Be Coarse

It is best to assert that "the answer contains some fact", not that it "equals some complete sentence".

A test set that alarms on a rewording will be learned to ignore quickly; once ignored, it is dead. This is a claim about scarce human attention:

> **The cost of verifying a system is not only machine time; it also includes the willingness of a human to look at it seriously.**

### 2.3 Tests Are Data Too

```yaml
- name: confusable.price-not-a-product-question
  question: "what is the price of dsh-review?"
  expect:
    refuses: true
```

Adding a phrasing adds a pattern; adding a guarantee adds a test. Both should be data that can be diffed.

### 2.4 The Accounting Between Data / git / CI

There is a common question here:

> If tests are data too, why not put them in the database instead of git files?

Because tests are not runtime knowledge. What runtime reads is "how to answer"; what a test answers is "what counts as correct". The two have different lifecycles:

- Knowledge must be executed;
- A test must gate one change.

A programmatic release process is actually longer:

```text
agent 编辑内容 -> 跑测试 -> 开 PR -> CI -> 人合并
```

The core is not GitHub; it is:

- tests are all green on main;
- a branch going red means a regression;
- `git revert` provides the rollback.

Regression evidence lives in git / CI, which looks like it conflicts with "move everything declarable to the data side". The way to handle it is to separate the two:

> **Runtime knowledge must be declared into data; verification evidence may be part of a gate, but it must be traceable to the specific change.**

If a future system needs a review interface that is not git, that is when proposals / test results need to become tables. Not now.

### 2.5 Dead Rows and Ambiguity Reports

Beyond the four kinds of test, you also need:

- knowledge rows that never match;
- phrasings that match multiple candidates;
- whether a new rule covers the scope of the old one;
- real missed questions clustered by shape.

These checks decide whether to "add a rule" or "change the structure".

## 3. Authority: Who May Change What

For verification to hold, the boundary must be real.

### 3.1 "Please Don't Cross the Line" Is Not a Boundary

Writing a boundary into the prompt is a request, not a constraint. As long as the agent has a shell, a filesystem, and a database, it can write straight to the database, change the engine, or change the test to make the test pass.

A maintainable system needs tool enforcement:

```text
read:  content/**, read-only projection
write: content/** (or proposals)
deny:  engine/**, schema, direct live writes, merge
```

### 3.2 Why

The principle:

> Answering users and writing system state should not both be held by the same process at once.

If AI on the request path can both answer and write knowledge, a wrong answer immediately becomes "system knowledge", with no review and no rollback.

Even outside runtime, an agent editing the live database directly is a problem: the change is not in the diff, reviewers cannot see it, and a rebuild may overwrite it.

### 3.3 Two Legitimate Writes

**PR / diff**: edit the offline files, open a branch, run the tests, open a PR, a human merges. Review, history, and rollback are all provided by git.

**Proposal tables**: only when reviewers do not use git, or when you need to learn quickly without merging, do you need `proposals` + a review interface + a state machine + a publish path. This is an exception, not the default.

### 3.4 The Allowed Surface Must Be Wide Enough

A boundary that is too strict also fails: if the agent cannot read data, look at statistics, or run tests, it will look for a way around to finish the task.

A usable boundary usually includes:

- read-only data queries;
- reading and writing content files;
- build / test commands;
- viewing missed questions and statistics;
- an explicit way to submit.

### 3.5 Role Permission Table

| Role | Read | Write | Must not |
|---|---|---|---|
| End user | Their own conversations | Ask questions / act | See internal data |
| Operations | Dashboards, review queue | Publish decisions | Change the engine |
| AI maintainer | Read-only projections, evidence, content | Content / proposals | Write online tables directly, merge |
| Developer | Everything | Engine / schema / migrations | Bypass review |
| Runtime | Data projections | Runtime state | Change knowledge |

## 4. Wake Cost

### 4.1 Three Ledgers

| Source | Count scales with | Handling |
|---|---|---|
| A. Runtime fallback | Requests × (1 − coverage) | Avoid it; if used, keep the evidence |
| B. Maintenance rounds | Frequency of structure change | Batched, offline, through tests and review |
| C. Build / sync | Volume of data | Zero model calls |

The goal:

> Make AI calls proportional to structural change, not to traffic or data change.

### 4.2 The Cost Formula and One Warning

```text
N  = 每周期请求数
c0 = 确定性解析单次成本
ca = 运行时兜底单次成本
κ  = 确定性覆盖率
w  = 每周期维护唤醒次数
cm = 单次维护成本（模型 + 上下文 + 人工评审）

C(N, w) = N * [c0 + (1 - κ) * ca] + w * cm
```

If one maintenance round raises coverage by `Δκ`:

```text
benefit = N * Δκ * ca
值得做当且仅当 N * Δκ * ca > cm
```

But this formula carries several strong assumptions worth writing down:

- maintenance cost is approximately linear in `w` — that may hold once context and review are amortized, or it may not;
- `Δκ` does not decrease — in practice improvements get harder later;
- adding structure does not raise `c0` — the more rules, the slower parsing may become.

So the formula is not a prophecy; it is a framework for asking whether this round of maintenance is worth it.

### 4.3 A Sample Calculation

```text
N = 10,000 请求/天，ca = 0.01，cm = 0.50
覆盖率从 90% 到 92%：benefit = 2 > 0.50
覆盖率只提高 0.1%：benefit = 0.1 < 0.50
```

The numbers are illustrative only.

### 4.4 Wake Strategies

| Mode | Fits | Risk |
|---|---|---|
| Per request | Cold start, first exploration | Uncontrolled cost |
| Micro-batch | Catch-up learning after a peak | Delayed feedback |
| Daily / weekly | Stable business, batch review | Slow when new problems pile up |
| Event-triggered | New catalog, new policy | Hard to tune thresholds |
| Manual | Low traffic, high sensitivity | Goes stale |

### 4.5 Fallback Is Not the Same as the System Knowing

A model fallback can be an optional layer, but it must:

- be enabled by a human decision;
- questions it has answered are still recorded as unresolved;
- the model sees only the relevant entities, not the whole database;
- refuse safely on timeout / error / invalid key.

The reason:

> **Answering a visitor does not mean the system knows.**

## 5. Two Real Cases as Evidence

### 5.1 personal-chatbots

A minimal implementation: 5 tables, offline content, a runtime projection, and the online `messages` table. As of writing:

- 24 knowledge rows;
- 48 frozen cases;
- unit and invariant tests;
- the browser build runs the same set of frozen cases, and CI does a parity check.

What it proves is how small the structure above can get.
It also proves something narrower: the deterministic layer takes about 0.2 ms and 0 tokens; the model fallback takes about 7 seconds. What differs is not the token unit price but where the wake happens.

### 5.2 MaaFwPhoneAI

The second domain is Android GUI automation:

- the workflow is a MaaFramework pipeline graph in the database;
- AI only writes proposals; after review they become the live pipeline;
- each execution saves its postconditions and evidence;
- verified flows enter 0-token replay.

The PC prototype already verified "the AI runs it once, then 0-token replay"; the Android side is still converging. It proves the structural logic does not depend on the text domain, and it also exposes more runtime complexity.

## 6. Notes and Limits

- The four kinds of test only certify known failure classes; they cannot prove correctness in unknown situations.
- This essay does not fully solve the problem of tests and rules sharing one origin. Solving it would require part of the verifier to be independent of the thing being verified, which is probably the next stage of work.
- If models become cheap, stable, and auditable enough, the defects of runtime agents will shrink; but this structure still solves "accumulable and rollback-able".
- If the review cost of a change stays higher than editing the code directly over the long run, this structure is not worth it.
- Author's position: I do not think "letting AI judge itself" can become a long-term trust mechanism; trust must come from an independent checker.
- The biggest cost of this method is review bandwidth. Automation can speed up checking, but it cannot produce judgment on its own.
