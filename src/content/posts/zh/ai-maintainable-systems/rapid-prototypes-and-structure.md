## 1. 一个很典型的周五下午

假设你想快速做一个聊天机器人，或者任何会用上 AI 的小应用。你想验证的是“有没有人用”，不是“能不能写成教科书架构”。于是你很自然地不想写数据访问层、迁移、权限、渠道、读写模块和评审流程。

然后你看到两条捷径。

**捷径一：把 agent 当后端。**

```python
# 伪代码：把 agent 命令包成一个 API
import subprocess
from fastapi import FastAPI

app = FastAPI()

@app.post("/chat")
def chat(question: str):
    result = subprocess.run(
        ["claude", "-p", question],   # 或 opencode -c、其他 agent 命令
        capture_output=True, text=True,
    )
    return {"answer": result.stdout}
```

用户请求进来，直接转给 agent。你不写表结构、权限、渠道、读写模块，一个下午就能演示。这不是在写系统，是在让 agent 临时扮演整个系统。

**捷径二：先写硬编码，再让 agent 维护。**

```python
if "price" in question and "iphone" in question:
    return "iPhone is $999."

if "refund" in question:
    return "Refunds are available within 14 days."
```

它运行时更稳定、更便宜。快速原型阶段，这是合理选择。问题是之后：价格变了改分支，问法变了加分支，错误丢给 agent 改代码；重复几十次后，没有人能完整说出系统现在知道什么。

## 2. 低流量下，两条捷径都可能是对的

必须承认一个反例：

> 如果原型只活三天，流量很低，模型便宜到可以忽略，系统几乎不变化——两条捷径都是理智的。

短路原型不是罪，把一次性原型当成会持续成长的系统才是。

所以真正要判断的是：

- 它会不会持续变化？
- 变化时需不需要被验证？
- 除了作者，还有没有人需要评审 / 理解它？
- 出错时，损失只是一次 demo，还是客户已经依赖它？

只要有一个答案是“是”，捷径就会开始变贵。但它们共同的问题不是“用了 agent”或“用了硬编码”，而是：

> **系统没有给变化一个可验证的落点。**

Agent 当后端，落点不存在；硬编码 + agent 维护，落点是最难验证的代码。

## 3. 一个太快得出的结论

到这里，很容易得出结论：

> 那就让 AI 改数据，不要改代码。数据比代码更适合 AI 维护。

这个结论走得太快了，而且会把整季带向一个错误前提。

它错在两点：

1. **代码不是坏的。** 算法、副作用、性能、安全边界、事务、外部系统交互，本来就应该由代码表达。
2. **数据不是自动可维护的。** 一堆没有词汇、没有表结构、没有校验的 JSON，只会把结构藏进约定里，比代码更难验证。

真正的问题不是“代码还是数据”，而是：

> **哪些东西应该被声明成数据，哪些必须留在代码，边界在哪里，谁负责守边界。**

“数据比代码高级”是一种偷懒的说法；正确的问题是结构放在哪里。

## 4. 代码和数据是两种材料

可以把代码和数据当成两种材料，而不是两个等级。

| | 代码 | 数据 |
|---|---|---|
| 擅长 | 算法、副作用、I/O、性能、安全、不变量 | 事实、规则、文案、配置、内容 |
| 可验证性 | 依赖测试、运行路径、边界 | 可寻址、可比较差异、可校验 |
| 爆炸半径 | 调用链、时序、异常路径 | 通常限制在行 / 实体 / 规则 |
| 修改者 | 开发者 + AI（高风险） | 人和 AI（可评审） |
| 失败方式 | 运行到某条路径才发现 | 写入时可以被拒绝 |

数据更适合 AI 维护，不是因为数据更高贵，而是因为：

- 它可以有稳定标识；
- 改动通常是局部的；
- 上下文可以裁剪；
- 可以被幂等重建；
- 可以在写入时校验。

但这些性质只对**有结构的数据**成立。自由文本和乱放 JSON 不具备它们。

代码仍然承担它擅长的工作：定义 原语、执行算法、处理副作用、守住安全边界。代码不是被“搬掉”，而是退到更少、更稳定的位置：

```text
System = Code + Data
```

代码负责解释、校验、执行、审查；数据负责承载知识、规则、变量、流程和状态。

当代码只解释词汇表、不逐条实现业务时，它接近 **meta-code（元代码）**：

> 如果代码规模随领域对象数量增长，它是业务代码；
> 如果代码规模只随词汇表大小增长，它才配叫 meta-code。

## 5. 什么时候应该把行为放进数据

不是所有东西都应该数据化。一个判断清单比口号有用：

- **变化频率**：它经常变吗？经常变的事实更适合数据。
- **可寻址性**：能给它一个稳定标识吗？价格、规则、文案可以；一段控制流通常不行。
- **评审需求**：改动需不需要被非程序员看懂？
- **验证方式**：能不能写测试 / 校验，而不是只能靠运行？
- **爆炸半径**：改错了影响一行，还是一条调用链？
- **上下文大小**：AI 能不能只读一小块就完成修改？

反过来，以下通常应该留在代码：

- 算法和性能敏感路径；
- 外部副作用和 I/O；
- 并发、事务、安全边界；
- 无法用数据词汇表达的原语。

这不是“把代码搬空”，而是把**可声明的知识**从代码里拿出来，让代码只保留它最擅长的部分。

### 5.1 一个最小规则：值不进句子

变化速度比句子更快的东西，不要写进句子里。

价格、版本、库存、日期、star 数属于数据；句子属于模板。这样一次数据变化只需要改一行、做一次重建，而不是改 N 条答案，更不需要唤醒模型。

## 6. 结构是边界，不是口号

当你说“用结构”，具体指的是什么？至少包含五件事：

1. 数据用什么词汇表达（实体类型、关系类型、动作类型）；
2. 数据用什么形态承载（行、JSON、文件、列）；
3. 哪些字段被声明、哪些留着自由；
4. 谁来校验、谁来评审、怎么回滚；
5. 状态和构建产物怎么分开。

结构不是“表越多越好”，也不是“代码越少越好”。它是一份关于边界的契约。

这个契约里最困难的一条是：

> **通用化到哪一步，领域特定化到哪一步？**

## 7. 核心张力：通用数据 vs 领域表

一个具体例子会让这个张力变清楚。

商品可以写成通用实体：

```json
{
  "entity_type": "product",
  "key": "sku:iphone-17",
  "attrs_json": { "price_cents": 99900, "stock": 12 }
}
```

好处是扩展便宜：新增领域不用迁移，AI 加数据就行。

但三个月后，你可能会看到：

```json
{"price_cents": 99900}
{"price": 999}
{"priceCents": 99900}
{"price_usd": "999.00"}
```

命名开始漂移；价格可以是负数；库存可以是字符串；“上架但无价格”没人知道是否合法。查询也变丑：每次都要写 `json_extract`，性能依赖约定。

另一个极端是建 `products` 表：类型、约束、查询都强，但每次领域变化都要迁移，AI 不能再靠“加数据”扩展。

于是问题不是“数据化还是代码化”，而是：

- 通用数据用**扩展性**换**结构强度**；
- 领域表用**结构强度**换**演化成本**；
- 选择取决于当前哪种成本更痛。

这就是数据与代码的辩证：**不是谁更高级，而是结构放在哪一层。**

## 8. 失败条件与作者立场

这套方法什么时候不成立？

- 如果系统几乎不变化，结构投入收不回来；
- 如果模型便宜、稳定、可审计到可以接受运行时 agent，临界点会移动；
- 如果每次变化都需要新增 原语，而不是新增数据，通用结构就失败了；
- 如果维护成本长期高于直接改代码，结构就是不划算的。

作者立场：我不认为“数据比代码好”或“代码比数据好”是有意义的争论。有意义的问题是：

> **这部分行为的变化频率、验证需求和爆炸半径，决定了它应该住在代码还是数据；而边界必须被明确声明，而不是靠约定维持。**

## 9. 下一个问题

现在框架有了：代码和数据是两种材料，结构是两者的边界契约，核心张力是通用数据 vs 领域表。

但边界具体怎么划？什么时候一个“可以有通用实体”的项目，真的需要一张 `products` 表？为什么不是永远不需要？
