## 0. 上篇留下的边界问题

上篇的结论是：代码和数据是两种材料，结构是两者的边界契约；其中最困难的一条是 **通用数据 vs 领域表**。它停在了一个具体问题上：

```text
entities + entity_links + attrs_json
```

商品可以只是：

```json
{
  "entity_type": "product",
  "key": "sku:iphone-17",
  "attrs_json": { "price_cents": 99900 }
}
```

但这立刻带来一个问题：

> 既然商品可以是通用实体，为什么还需要 `products` 这种领域表？  
> 如果永远不需要，结构住在哪里？  
> 如果需要，为什么不是一开始就需要？

这篇不急着给答案。先把两个极端都推到失败，再从失败里推导边界。

## 1. 先认真待在“全通用”这一端

假设我们真的坚持：

- 没有 `products` 表；
- 没有 有类型的列；
- 所有业务事实都放进 `attrs_json`。

一开始它很好用：新增领域不用迁移，AI 加几行数据就行。

然后系统开始变大。第一个失败是**命名漂移**。

三个月后，查询价格时你可能看到：

```json
{"price_cents": 99900}
{"price": 999}
{"priceCents": 99900}
{"price_usd": "999.00"}
```

没有人故意制造分歧；只是不同的人、不同的 agent、不同的时间，做了不同的命名选择。数据库没有拒绝过任何一条。

第二个失败是**校验退化**：

- 价格可以是负数；
- 单位可以是 USD、HKD，也可以没有；
- “库存”可以是数字、字符串或缺失；
- 已下架商品可能仍然有价格，但没人知道这是不是合法状态。

第三个失败是**查询变丑**：

```sql
SELECT *
FROM entities
WHERE entity_type = 'product'
  AND json_extract(attrs_json, '$.price_cents') > 10000
  AND status = 'live'
```

一旦这种查询变多，性能、索引和可读性都会开始付代价。

这说明：

> **通用化不会消灭结构，它只是把结构从表结构转移到了约定、命名和查询里。**

结构变成了**重建结构**：每个读它的人、每个 AI 会话、每次调试，都要重新把它拼出来。

### 1.1 声明结构与重建结构

同样的结构，可以住在两个地方：

- **声明结构**：列、约束、词汇表。写的时候声明一次，引擎和数据库会读它；
- **重建结构**：命名约定、注释、JSON key。每个读者、每个 AI 会话、每次查询，都要重新把它拼出来。

目标不是消灭结构，而是最小化重建结构。

### 1.2 交接说明有多长

一个可操作的检验：

> **交接说明有多长？** AI 或新维护者行动前需要被告知的每句话，都是还没有声明出来的结构。

但声明结构也有成本：迁移、耦合、一个设计错的列删起来比加更难。所以目标不是结构越少越好，而是把必须保留的声明结构压到足够小。

## 2. 再认真待在“每个领域一张表”这一端

另一个极端是每来一个领域就建表：

```text
products
orders
coupons
flows
rules
...
```

它查询方便、约束强、团队熟悉。但代价是：

- 新领域需要迁移和部署；
- AI 不能真正扩展系统，只能改已有领域；
- 很多结构重复：状态、来源、时间、审计；
- 领域一变化，表结构跟着变。

它的失败方式不是“无法表达”，而是“无法轻量演化”。

## 3. 不急着合成：用同一种货币比较

两个极端不是“一个更先进”，而是把同一种成本放到了不同地方。可以用四个维度比较：

| 维度 | 全通用实体 | 每领域一张表 |
|---|---|---|
| 新增领域 | 加数据，0 迁移 | 加表，1 迁移 |
| 查询和约束 | 弱，依赖 JSON 和约定 | 强，数据库可强制 |
| 可读性与交接说明 | 每个读者要自己重建 |表结构直接说明 |
| 演化成本 | 低（数据层），高（语义层） | 低（语义层），高（表结构层） |

真正的问题不是“要不要领域表”，而是：

> 把结构放在约定里，还是放在表结构里？  
> 哪一种成本在当前系统里更痛？

## 4. 从失败推导提升条件

提升条件不应该是清单，而应该是从上面失败里推出来的。

### 4.1 当数据不再是“东西”

订单行、库存流水、价格历史不是实体，它们是事件 / 状态变化。把事件硬塞进 `attrs_json` 会让查询和时间关系变得别扭。这时需要事实表。

### 4.2 当数据库能强制、而校验器很难强制

多列唯一、外键、跨行 CHECK 这类约束，数据库天然更强。如果这些约束是业务正确性的前提，就值得提升。

### 4.3 当查询痛苦是测量出来的，不是想象出来的

JSON 查询慢不是因为你“感觉 50k SKU 会慢”，而是因为：

- 有真实慢查询；
- 有真实索引需求；
- 有真实聚合和排序。

measure 之后再拆。

### 4.4 当外部表结构不允许你选择

对接 ERP、支付、库存系统时，对方给你一个固定表结构。你不再设计它，只能适配。

### 4.5 两个反例

上面这些条件成立，也可能还不该提升：

- 数据量很大，但查询很少、很冷，瓶颈不在 JSON；此时优化可能只是早期复杂化。
- 查询很痛，但可以通过物化视图或索引优化解决，不一定要改主模型。

上面这些条件不成立，也可能必须提升：

- 外部表结构强迫你；即使内部没有查询痛点，也得上表。

所以提升不是规则表，而是：

> 当某一种成本真实地压过了另一种，才移动边界。

## 5. 一次真实的提升：知识模板不动

下面演示一次提升，重点不是 SQL 多优雅，而是**知识层不用改**。

### 5.1 提升前

实体行：

```json
{
  "entity_type": "product",
  "key": "sku:iphone-17",
  "attrs_json": { "price_cents": 99900 }
}
```

知识行：

```yaml
- slug: product.price
  patterns: ["how much is {product}"]
  slots: { product: product }
  action:
    kind: answer
    template: "{product} is {price}."
```

测试：

```yaml
- name: product.price.iphone
  question: "how much is iphone-17"
  expect:
    resolves: { product: "sku:iphone-17" }
    answer_contains: ["999.00"]
```

### 5.2 提升后

新增 `products` 表，实体主干仍然保留：

```sql
CREATE TABLE products (
  entity_id    INTEGER PRIMARY KEY REFERENCES entities(id),
  price_cents  INTEGER NOT NULL,
  currency     TEXT NOT NULL DEFAULT 'USD',
  stock        INTEGER NOT NULL DEFAULT 0
);
```

存储层读价格时，从 `products` 取，而不是从 `attrs_json` 取。但：

- 知识模板（`knowledge`）仍然是 `{product}` 和 `{price}`；
- 解析器返回的上下文仍然包含 `price`；
- 测试用例不需要重写；
- 变的只是数据投影和 SQL。

这就是参数化的回报：

> **存储形态可以变，知识的句子不用变。**

## 6. 领域表也是一次命名行为

还有一层经常被忽略：`products` 这个词本身在替未来读者做命名工作。

`entity_type='product'` + 词汇表条目，把“这是什么东西”的定义分散在代码、数据、文档和人的记忆里；`products` 表把这份定义声明在一个地方。

这是它的优势，也是它的成本：

- 优势：交接说明变短，读者更快知道这里放什么；
- 成本：命名一旦公开就很难改，表的耦合会把未来的选择锁住。

所以“领域表 = 命名行为”不是一句修辞，它意味着提升时要额外问：

> 这个名字是否稳定到值得成为表结构的一部分？

如果答案不确定，也许先让它以 词汇表 / entity_type 的形式存在，等证据足够再固化。

## 7. 四个家：结构最终住在哪里

无论提升与否，结构都要分到四个家：

| 家 | 谁改 | 改动意味着 |
|---|---|---|
| 配置 | 人 | 一次部署 |
| 内容 | 人和 AI（经评审） | 一次 PR |
| 数据 | 构建流程 | 一次重建 |
| 状态 | 运行时 | 追加；永不重建 |

进一步两条线：

- **离线 / 在线**：内容离线可比较差异；投影在线可查询；运行时只读投影；
- **构建 / 在线**：构建表无状态；状态只在在线表。

这四条边界比“有没有 products 表”更重要。它们决定了：

- AI 改的是哪一层；
- 重建 会不会伤害状态；
- 评审看到的是什么；
- 一个新增结构应该落到哪里。

### 7.1 状态也要被赚得

领域表不是唯一会被过度建立的东西，状态表也一样。

“第二个”可以从上一轮引文重写出来，不需要状态表；只有某个值必须跨轮保留（“几个人？” -> “3”）时，流程与状态才值得存在。反过来，GUI 自动化里的步骤状态是真需求，因为识别与动作本来就有先后和分支。`MaaFwPhoneAI` 就是一个状态必须被建出来的域。

所以状态不是禁忌，而是必须由跨轮值或副作用来赚得。

## 8. 说明与边界

- 本文不主张“永远不要领域表”。它主张的是：提升由真实成本触发，而不是由直觉触发。
- 如果业务天然要求强事务、强约束、大量查询，领域表可能第一天就该存在。
- 如果团队没有能力维护表结构，通用实体更合适；如果团队没有能力维护约定，领域表更合适。
- 作者倾向于：先用通用结构换演化速度，等一种成本真实地压过另一种，再提升。

## 9. 下一个问题

数据化的边界有了，知识句子的稳定性也有了。但还有一个问题没有回答：

> **AI 改了数据 / 结构之后，我们怎么知道这次改动真的让系统变好了？**

这正是下一篇的主题：验证、权限与唤醒成本。
