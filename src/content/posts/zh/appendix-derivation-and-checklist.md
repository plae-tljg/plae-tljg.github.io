这不是正文，而是前 3 篇的配套工作文档。

## 1. 推导链

不要从“用哪张表 / 哪个 agent”开始，而从目标和约束开始：

```text
Goal -> Actors -> Intents -> Information shapes
     -> Structures -> Columns -> IO -> Wake policy
```

### 1.1 Goal

一句话：为谁解决什么。包含终端用户、他们要完成什么、哪些事情必须由人接手。

### 1.2 Actors

至少区分：

| 角色 | 关心什么 |
|---|---|
| 终端用户 | 是否被回答 / 操作是否完成 |
| 运营 / 客户 | 知识是否正确、能否评审发布 |
| AI 维护者 | 读什么、写什么、如何验证 |
| 开发者 | 引擎、表结构、迁移、权限 |

### 1.3 Intents

列真实意图：查事实、查实体属性、条件判断、多轮澄清、副作用 / 交人、未知。

### 1.4 Information shapes

| 形态 | 适合结构 |
|---|---|
| 静态事实 | 知识行 / 文案 |
| 参数化事实 | 模板 + 实体行 |
| 条件路由 | 规则行 / 小 DSL |
| 跨轮指代 | projection，不用状态表 |
| 多轮收集 | 流程 + 状态 |
| 副作用 | task / 外部动作 |
| 未知 | 拒答 + 收件箱 |
| 复合问句 | 解析算法，不是表 |

### 1.5 Structures

- 放配置、内容、数据还是状态？
- 优先：配置文件 > 内容文件 > 已有表 > 新表；
- 默认：通用实体 + link + JSON 属性 + 小词汇表；
- 提升由真实成本触发，不由直觉触发。

### 1.6 Columns

- 会查询、连接、过滤、约束、统计的字段 -> 有类型的列；
- 领域相关、只随行携带的字段 -> JSON；
- 需要双向关系 -> link 表；
- 不再是实体形状 -> 独立事实表。

### 1.7 IO

| 角色 | 读 | 写 |
|---|---|---|
| 终端用户 | 对话 | 提问 / 操作 |
| 运营 | 面板、评审队列 | 发布决策 |
| AI 维护者 | 只读证据、内容 | 内容 / 提案 |
| 运行时 | 数据投影 | 运行时状态 |

### 1.8 唤醒策略

- 运行时是否允许模型兜底？
- 维护是每日、事件触发还是手动？
- 哪些数据变化根本不需要模型？
- 模型回答过的未命中是否保留证据？

## 2. 一个练习：预约助手

目标：用户可以预约，复杂预约交给人工。

| Intent | Shape | Structure |
|---|---|---|
| 营业时间 | 静态事实 | 知识行 |
| 有哪些服务 | 参数化事实 | 实体 + 模板 |
| 周末能不能约 | 条件规则 | 规则行 |
| “第二个服务” | 指代 | 上一轮引文 |
| 预约需要哪些信息 | 多轮收集 | 流程 + 状态 |
| 提交后通知工作人员 | 副作用 | task |
| 未知政策 | 未知 | 拒答 + 收件箱 |

## 3. 结课清单

### 问题

- [ ] 我面对的是运行时 agent 不稳定，还是硬编码维护不可验证？
- [ ] 问题会持续成长，还是一次性？
- [ ] 我是否把“修好一个例子”当成“变好”？

### 结构

- [ ] 业务事实还有多少住在代码里？
- [ ] 配置、内容、数据、状态是否分开？
- [ ] 离线 / 在线、构建 / 运行时边界是否清楚？
- [ ] 值进句子了吗？
- [ ] 新结构有真实触发条件吗？

### 验证

- [ ] 每个行为改动有测试吗？
- [ ] 有正例、易混负例、拒答、歧义四类吗？
- [ ] 有回归基线和回滚路径吗？
- [ ] 有死行 / 歧义报告吗？

### 权限

- [ ] AI 的读 / 写 / 禁止集合是什么？
- [ ] 权限是工具强制还是 prompt 请求？
- [ ] AI 能否直接写在线表、直接合并？
- [ ] 评审能否在有限上下文内完成？

### 成本

- [ ] 运行时唤醒几次？维护唤醒几次？
- [ ] 哪些变化会唤醒模型？
- [ ] 兜底是否仍记录 unresolved？
- [ ] 覆盖率、兜底率、单位成本有记录吗？

## 4. 反模式

- 把所有逻辑塞进代码；
- 把 agent 放在运行时；
- 让 agent 直接改在线状态；
- 没有测试就让 agent 维护；
- 所有东西都塞 JSON；
- 为未来预留空表；
- 用模型兜底却清掉 unresolved；
- 用模型回答来假装结构已经知道答案。

## 5. 什么时候不该用这套东西

一次性脚本、没有持续演化需求的小工具、完全没有重复决策的探索任务——简单脚本就是正确答案。

结构化有成本，不值得的时候不要用它。

## 6. 术语表

| 术语 | 含义 |
|---|---|
| 可维护 | 改动可执行、可验证、可回滚、可累积、可负担 |
| 结构 | 代码与数据之间的契约：行、表结构、词汇、校验、流程 |
| Data | 可声明层：知识、规则、变量、流程、测试、内容文件 |
| meta-code | 代码规模随词汇表增长、而不是随领域增长的解释器 / 校验器 / 运行器 |
| 四个家 | 配置 / 内容 / 数据 / 状态 |
| 离线 / 在线 | 可编辑、可比较差异的形态 vs 可索引、可查询的投影 |
| 构建 / 在线 | 构建表 vs 运行时状态表 |
| 重建结构 | 未声明、每次都要重新推导的结构 |
| 指代 | 从上一轮引文推导的跨轮引用，不需要状态表 |
| 流程 / 状态 | 只有值必须跨轮保留时才需要的运行时状态 |
| 唤醒 | 唤醒模型：运行时兜底 / 维护轮 / 构建 |
| 兜底（fallback） | 结构答不出时的模型回答；仍记录 unresolved |
| 提案 | 可审核、可回滚的改动；git PR 或提案表 |
| κ | 确定性覆盖率 |
| 死行 | 从未命中的知识行 |

## 7. 最后四个问题

如果 AI 改了一个数据 / 内容，你能回答下面四个问题，这个系统就在正确方向上：

1. 为什么改？证据是什么？
2. 改了什么？差异在哪里？
3. 是否变好？测试和指标是否支持？
4. 错了怎么退回去？

能回答，结构就是可维护的；不能回答，模型再强也只是更快地在黑箱里改东西。
